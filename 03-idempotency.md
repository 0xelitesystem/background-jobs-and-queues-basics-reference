# Idempotency

Idempotency means that processing the same job more than once produces the same end state as processing it exactly once, with no extra side effects. It matters because real queue systems redeliver messages: a worker can crash after doing the work but before acknowledging it, a network blip can hide an ack, and the broker will then hand the job to another worker. If your handler is not idempotent, that redelivery charges a card twice, sends two emails, or inserts a duplicate row. Designing for safe replay is therefore not optional; it is the price of using a queue at all.

## Why duplicates happen

Duplicates are an unavoidable consequence of at-least-once delivery, not a rare bug. To guarantee a job is never lost, a queue only removes it after the worker acknowledges success, which means any failure between "work done" and "ack received" causes a redelivery. The worker may have fully completed the side effect, then died before acking, so the broker correctly assumes the job is unfinished and retries it. Because you cannot atomically perform an external side effect and an ack at the same time, you must assume the work can run again and make that harmless.

## Idempotency keys

Attach a stable, unique key to each logical operation and use it to detect and skip repeats. The key can come from the business event (an order ID, a payment request ID) or be generated by the producer and carried on the job. Before performing the side effect, the worker checks whether that key has already been processed, usually by inserting it into a table with a unique constraint inside the same transaction as the work. If the insert fails on a duplicate key, the work was already done and the worker simply acks and moves on.

## Designing idempotent handlers

Prefer operations that are naturally idempotent, and add a dedup layer when they are not. Database upserts (insert-or-update keyed on a unique column) and "set status to X" writes are idempotent by construction, because running them twice lands on the same state. Counters, appends, and external API calls are not, so wrap them with an idempotency key or use the provider's own idempotency support where it exists. The reliable pattern is to make the state change and the record-of-completion atomic, so a crash can never leave them disagreeing.
